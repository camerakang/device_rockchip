# SS-07 RK3588 视频与声呐系统需求整理

初次整理日期：2026-10-23；实现进度和设备状态更新至 2026-10-26。依据本项目对话、当前设计、留存的设备探测及用户提供的 SE2017 操作指南。本文汇总已明确需求与待确认事项；候选指标和设备枚举结果不代表实物验收通过。

2026-10-26 用户已确定五路 USB 按 **H.264 1280×720、25fps、2＋2＋1 接线**进行项目验收，不再以五路 1080p25 为必达项。完整验收范围、真实生产链路和证据门槛见[720p25 验收基准](acceptance-720p25.md)；其他功能及长期运行要求保留。

## 1. 项目目标与边界

在鲁班猫 LubanCat-4 / RK3588 上开发独立船端应用，接入六路视频和五路声呐，通过船岸有线网络提供浏览器监看、录像查询回放、设备状态与配置维护，并利用独立 RS485 时码输入关联录像和声呐记录。最终交付独立应用包及基于当前 SDK 构建的完整系统镜像。

| 纳入本工程 | 外部独立系统 |
| --- | --- |
| 五路 USB 相机、一路 SE2017 网络视频的采集/接入与分发 | 云台接收器及其电机控制、CAN、摇轮控制 |
| 五路 RS485 声呐采集与状态 | 已有跟焦遥控器—接收器—电机链路 |
| 监看网页、录像、存储、配置、日志、状态 API | mobocon、UE、风机设备及其软件 |
| 独立只读时码接收、时间映射与记录关联 | 时码发生器固件、公共控制协议维护 |

RK 不转发运动命令，不执行电机使能、控制权仲裁或时间轴。RK 应用停止、重启或视频网络故障不应改变云台、跟焦系统的控制权。公共协议库是设计和时码规则的来源；风机和接收器仓库只作为外部项目登记，不扩展成本工程交付。

## 2. 硬件连接与已知事实

最初连接为五台 USB 相机接 Hub。10 月 26 日为排查并发带宽，整个 Hub 改接 Type-C，随后逐台移出并复核端口；最新为 `fc880000` 两台、Type-C `fc000000` 两台、蓝口 `fc800000` 一台。鲁班猫网口接交换机，交换机分别接路由器和 SE2017。最终岸端浏览器通过船岸有线 Ethernet 访问 RK。

| 设备/链路 | 需求及当前证据 |
| --- | --- |
| RK 主机 | 地址 `192.168.3.233`，已按本轮验收授权正式部署 0.10.2 并通过真实 LAN 五路短测。该值是网络地址，应用逻辑 device_id 单独管理 |
| 五路 USB 视频 | 用户授权自行定义方向；原 Hub 的 1.2/1.3.1/1.3.2/1.3.3/1.3.4 依次标记 front/back/left/right/down。接线及相机交换改变了绑定，观测路径见[最新记录](target-probe-192.168.3.233.md#2026-10-26-三控制器五路对照与慢相机定位)，安装方向和重启后绑定仍需复核 |
| USB 模式 | 五台均枚举 H.264 1080p25；三个控制器各一路曾完整解码 750 帧。蓝口相机调整到明亮场景后单路为 24.977fps/750 AU；五路 720p25 延长对照各 1000 AU，共同 33.325 秒，约 24.91～25.01fps，经 libavcodec/Chromium 完整解码。仍有 V4L2 丢帧告警及 OpenH264 差异；当前五路 1080p25 仍有两路 STREAMON ENOSPC，未通过 |
| USB 身份 | 五台序列号均为 `00000000`，按固定 Hub 物理路径绑定，不能依赖冲突的 by-id 或 videoN 枚举编号 |
| USB 总线 | 全部相机为 480M USB2；共享控制器双路 1080p25 出现 STREAMON ENOSPC，三个控制器各一路出帧通过。当前为 2＋2＋1 分组，仍有共享主干；Hub 的 5000M 分支不能代表相机带宽 |
| 第六路视频 | 设计输入为 SDI 摄像机 → SE2017 → Ethernet → RK；SE2017 的 SDI LOOP OUT 可供外部监视器 |
| SE2017 地址与输出 | `192.168.3.47` 经用户提供账号认证确认为 SE2017 / V1.0.0.9 / Ethernet / SDI；实际 RTSP 为 `rtsp://192.168.3.47:5554/live/av`，开发机媒体/网页链路已通过；设备仍报告 SDI NoSignal，真实摄像机输入未验收 |
| 声呐与时码 | 声呐目前没有实物。时码为 USB-RS485，用户确认 500000 baud；适配器稳定路径及其余 UART 参数待确认。ttyACM0～4 为相机复合接口，不能当作声呐/时码 |
| 录像介质 | 用户确认按名义 1TB 规划，目前尚未连接；具体介质、挂载身份、可用空间和写速待确认 |

板端实测环境为 Ubuntu 20.04.6 / Linux 5.10.160 / Python 3.8.10 / GStreamer 1.18.5。首阶段开发机为 x86_64、Python 3.10.12，两者需做兼容性验证，不能把开发机通过直接视作板端通过。

**2026-10-23 复查更新**：当天 12:01 的真实探测中，192.168.3.233 没有枚举到 USB 相机或串口，仅见一个 Hub。上述五相机模式/身份仍是 10 月 21 日的历史证据；实际采集须待设备恢复并重新核验。见 [当天探测 JSON](evidence/rk3588-192.168.3.233-probe-20261023.json)。

**2026-10-24 复查更新**：SSH 只读复查仍为零个 video 和 USB/ACM 串口节点，仅见一个外接 Hub；块设备只有约 125 GB eMMC，没有 1 TB 录像盘。板端仍是原有 5.10.160 内核，本工程未部署。原始日志摘要与检查边界见[复查记录](evidence/rk3588-presence-20261024.json)。

**2026-10-24 下午复查**：仍无 `/dev/videoN` 相机字符设备、USB/ACM 串口及稳定路径，只有 eMMC；`/dev/video-enc0`、`/dev/video-dec0` 名称不能计作相机。SE2017 候选地址 HTTP 返回 AVMATRIX 页面，554 仍拒绝连接。见[本次原始记录及摘要](evidence/hardware-readiness-20261024-followup.json)。未安装应用、启动采集或修改设备设置。

SE2017 手册提供的接入依据：默认登录为 admin/admin（实际是否改密未知）；RTSP 示例为 `/live/av0` 主码流、`/live/av1` 子码流、端口 554；应从设备流设置读取实际“本地地址 URL”。手册说明 HTTP 流与 RTSP 流只能启用其中一个，局域网流/USB 采集模式切换会重启设备。这些说明不授权自动更改设备配置。

2026-10-24 后续认证已取得设备真实配置并完成无 SDI 输入时的编码输出链路检查，详见[认证与传输证据](evidence/se2017-authenticated-20261024.json)。设备使用 5554 端口及 `/live/av`，上文的手册地址仅保留为参考。

## 3. 功能需求

2026-10-26 最新明亮场景复测及当前“2＋2＋1”模式对照见[记录](target-probe-192.168.3.233.md#2026-10-26-明亮场景复测与五路模式对照)和[完整证据](evidence/usb-bright-five-camera-20261026.json)。此前 720p25 的超时、共同窗口不足及解码失败均保留；用户随后已将五路 USB 的验收模式确定为 720p25。短时可运行结果仍不替代生产链路、丢帧观测或长期验收。

2026-10-26 现场更新：用户重接先前拔下的相机 Hub 后，五台相机均已枚举，稳定路径与原 `fc800000.usb` 映射一致；五路均声明 H.264 1080p25。板端现有 GStreamer 对 front 短时采集 125 个 AU，开发机完整解码 125 帧，短时约 25fps，采集后恢复原模式。首轮精确计数条件失败及后续源计数复核均留存；不算持续无丢帧或产品链路验收。五路并发、网页、拔插与质量验收保留，见[当日证据](evidence/usb-cameras-20261026.json)。下述 10 月 24 日唯一 Hub 状态为历史记录。

现场后续确认：用户明确尚未连接 SDI 摄像机，需接入后再验收有效输入。当前唯一 USB Hub 接在 `fc880000.usb`，与历史相机示例的 `fc800000.usb` 不同；五路相机恢复后必须重新探测并确认固定方向路径，不能把历史绑定当作当前硬件事实。见[拓扑记录](evidence/usb-topology-20261024.json)。无 SDI 输入时现有输出已通过开发机隔离目录的分段/索引/导出/回放检查，见[录像证据](evidence/se2017-recording-20261024.json)；真实输入与介质门槛保留。

## 4. 稳定性与部署约束

- 相机、媒体、声呐、时码、存储和 API 分离职责；API 不直接持有视频设备或串口，API 重启不停止采集和录像。
- 允许部分设备可用；缺时码不阻塞录像，缺盘不阻塞监看，单个声呐超时不拖住整条总线。
- 队列、缓冲、重试和日志设上限；积压或丢失应可观察，不无限占用内存或磁盘。
- 配置、索引和录像保存在应用版本目录之外；systemd 管理服务和最小必要设备权限。
- 独立更新与回滚必须考虑数据库兼容性，不能只切换程序文件就认定恢复完成。
- 保留 SDK 中已有应用和用户未提交内容；在 `device/rockchip/apps/ss07-water-control` 内维护本工程，独立产物放 `output/ss07/`。
- 最终完整 IMG 必须能追溯启动组件、内核、设备树、模块、rootfs 和应用源码/依赖，不能仅重打包旧启动镜像声称完成源码构建。
- Git 提交、推送和烧写继续等待用户后续明确指令；本轮实际应用部署已纳入用户的五路 720p25 验收授权并执行，保留事务和现场变更记录。

## 5. 性能候选与验收

以下数值来自原设计，是待实测冻结的候选，不是已达成或已批准的最终承诺。

| 项目 | 候选值/要求 | 冻结条件 |
| --- | --- | --- |

| SE2017 | H.264 1080p30、约 6Mbps | 实际 SDI 输入、编码设置、RTSP 拉流和客户端兼容性验证 |

最终验收包括六路同时监看录像连续 8 小时；记录帧率、延迟、丢帧、CPU/内存、温度与存储变化。另覆盖相机拔插不换方向、编码器断网恢复、声呐坏帧/离线、时码零发送与失时恢复、缺盘/满盘/拔盘、冷启动、应用恢复，以及 RK 故障不改变外部运动系统控制权。8 小时为持续运行验收时长，不自动代表录像保留期限或容量已定。
